출시 앱의 실제 사용 현황과 기존 데이터는 미확인이다. 따라서 동명 함수를 즉시 교체하는 결정은 보류한다. 기존 앱이 사용 중이고 업데이트가 어렵다는 사실이 확인되면 Node.js에 보안·종료 정책을 먼저 보완하고 호환 기간을 두는 방향이 더 적절할 수 있다.

## 판단 기준과 비교

정책 기준은 [채팅 계약](../chat/chat-contract.md)이다. 이 문서는 정책을 새로 정의하거나 계약을 변경하지 않는다. 기존 배포 소스·실행 JavaScript에서 확인된 차이를 기준으로 두 구현 방향을 비교한다.

| 관점 | 기존 Node.js 보완 | Python 구현으로 단계적 교체 |
| --- | --- | --- |
| 변경 범위 | 기존 진입점 유지 가능. 계약에 맞춘 내부 구조 재작성이 필요 | 현재 서버 구현 재사용 가능. 데이터 변환·호환 처리가 필요 |
| 보안 | 세션 ID·만료, App Check, 대표 답변 제한, 종료 재개 차단을 추가해야 함 | 해당 검사가 구현돼 있음. 실제 callable·앱 통합 검증은 필요 |
| 앱 영향 | 이름을 유지해도 인증·읽음·종료 의미가 바뀜 | 이름·응답 키 보존 가능. 같은 정책 의미 변경이 발생 |
| 데이터 보존 | 기존 경로 유지에 유리. 현재 계약 경로와 연결 필요 | 이전 또는 호환 조회 구조 필요. 기존 ID·이력 보존 필수 |
| 검증 근거 | 배포 소스 확인 완료. 현재 계약 충족 테스트는 미검증 | MySQL 6개·Firestore 트랜잭션 3개·Rules 4개 통과. 실배포 통합은 미검증 |

확인된 계약 차이는 세션 ID·만료 검사 누락, App Check 강제 비활성, 직원 canReply 미검사, 기존 chatRooms와 새 chatRoomAccess 구조 차이, 상대별 읽음 번호와 전체 sequence 차이, 고객 unread 거절, 종료 방 재개 가능, 직접 FCM 발송과 업무 서버 알림 동기화 차이다. 런타임 차이 자체는 계약 불일치의 근거가 아니다.

## 1 백엔드 API 수정

관리자·고객 채팅 세션 API의 경로와 응답 형식은 유지한다. 주요 보완 대상은 기존 데이터와의 연결이다.

- 기존 Firebase UID와 관리자 ID의 대응을 확인한다. 다른 UID에 기존 대화를 자동 연결하지 않는다.
- 예약 동기화가 기존 roomId를 재사용하도록 매핑을 추가한다. 최초 유효 문의→예약 전환은 같은 방을 유지하고 복수 예약은 별도 방으로 연결한다.
- 동명 문서를 새 형식으로 무조건 덮어쓰지 않도록 구조 확인·변환·동기화를 분리한다.
- 종료의 blocked/closed, 세션 회수, SQL 알림함 eventId는 하나의 기준으로 유지한다.
- 공유 DB를 사용하는 다른 서버의 소속·권한 변경에도 즉시 채팅 회수를 연결한다. 함수 교체만으로 해결되지 않는다.

기존 채팅 경로·필드 지원을 위한 구체적인 API 수정 범위는 출시 앱과 기존 문서 구조 확인 후 확정한다. 새로운 인증 체계를 추가하는 대신 현재 업무 세션 검증과 custom token 발급 흐름을 재사용한다.

## 2 Firebase 함수와 Rules 인덱스 스케줄 수정

다섯 callable의 이름과 기본 요청·응답 키를 유지하는 방향이다. 세션 ID·만료, App Check, 대표 답변 제한, 개인 읽음, 문의 168시간 만료, 예약 종료 불가역 정책을 적용한다. 같은 이름의 함수라도 내부 데이터 구조와 동작이 달라지므로 단순 배포만으로 호환을 보장하지 않는다.

| 대상 | 수정안 |
| --- | --- |
| ensureInquiryChat | 선택 productId 검증·최근 상품 갱신, 열린 문의 재사용, 종료/만료 후 새 문의방 생성 |
| ensureBookingChat | 현재 예약 매핑의 실제 roomId 사용, 최초 문의 전환 시 메시지·읽음 보존, 계약 오류 코드 적용 |
| sendChatMessage | 현재 세션·전송 권한·종료/만료 검사, 원문과 표준 UUID 검증, 같은 ID 재시도 처리, 발신자 읽음 갱신 |
| markChatRead | 사용자별 전체 sequence 기준의 누적 읽음, 기존 읽음 변환/호환 처리 |

Rules는 필요한 기존 조회 경로와 새 경로에 동일한 세션·직접 소속 제한을 적용하고 클라이언트 직접 쓰기를 금지한다. 호환 조회 구조를 유지해도 일반관리자 답변·상위 조직 권한 상속·이전 세션 접근을 허용하지 않는다.

현재 계약용 인덱스 4개는 2026-10-12 READY로 확인했다. 추가 인덱스는 실제 앱 쿼리를 확인한 뒤 정한다. 만료와 업무 동기화는 각각 단일 실행 주체를 확인한다. 실제 만료 스케줄 및 다른 cron/외부 작업의 존재는 아직 확정하지 못했다.

default/nodejs22 동명 함수를 nadree-chat/python312로 전환하는 절차는 격리 환경에서 확인해야 한다. 함수별 소유 codebase·진입점·런타임·트리거·가용성 영향을 명시하고 기존 함수 삭제/재생성을 요구하는 경우 별도 승인 대상으로 다룬다. 전체 배포와 암묵적 삭제를 자동 승인하지 않는다. [Firebase 함수 관리](https://firebase.google.com/docs/functions/manage-functions)

필요한 자료는 출시본과 일치하는 소스·커밋, callable 호출 코드, Firestore 쿼리, 로그인·푸시 처리 코드, 출시 버전별 사용 현황이다. 특히 setChatStatus의 open 호출과 읽음 position 해석 방식을 확인해야 한다. 이 자료 없이 앱 업데이트 규모, 구버전 지원 기간, 앱 수정 없는 교체 가능 여부를 추정하지 않는다.

## 4 기존 채팅 데이터 이전 필요 여부

기존 문서 수·실제 사용 상태가 미확인이므로 이전 필요량은 확정하지 않는다. 문서 구조와 사용 현황에 따라 아래 기준으로 결정한다.

| 데이터 상태 | 처리 방향 |
| --- | --- |
| 실제 데이터 없음 | 이전 없이 새 구조 사용 가능. 미사용은 함수 목록이나 실패 요청 로그만으로 판정하지 않음 |
| 기존 방·메시지 있음 | 삭제 없이 새 구조에 연결하거나 복사. roomId·messageId·본문·순서·시각 보존 |
| 기존 예약 연결 있음 | 예약 ID와 방 매핑 보존. 문의와 예약을 추정해서 합치지 않음 |
| 기존 읽음 있음 | 상대별 번호를 전체 sequence로 변환하는 규칙 필요. 숫자 그대로 복사하거나 미읽음을 임의 읽음 처리하지 않음 |
| 기존 토큰·세션 있음 | 현재 업무 세션 검증 후 재발급. 기존 토큰·기기를 임의 승계하지 않음 |
| 미처리 알림 job 있음 | 중복 방지 기록 보존, 재발송 여부와 전환 기준 별도 결정 |

기존 구조가 사용 중이면 호환 조회용 문서를 필요한 기간 보존하고 쓰기는 한 처리 경로에서 관리한다. 메시지 백필이 기존 트리거를 통해 실제 고객에게 푸시를 발생시키지 않도록 차단·변환 계획을 먼저 검증한다.

확정에 필요한 자료는 비식별 문서 수·필드 구조·최근 쓰기 시각·예약 연결 현황과 백업이다. Firestore 백업/복원과 계약 구조 변환은 별개 작업이다. [Firestore 백업과 복원](https://firebase.google.com/docs/firestore/manage-data/export-import)

## 5 배포 순서 검증과 실패 시 복구

1. 출시 앱·기존 데이터·스케줄을 확인하고 지원 앱 버전, 호환 기간과 최소 지원 버전을 결정한다.
2. 배포 소스·설정, Rules·인덱스·스케줄, Firestore·SQL의 복구 지점을 확보한다. 비밀 설정 백업은 접근 제한 저장소에 보관하고 소스/문서에 기록하지 않는다.
3. demo 에뮬레이터와 폐기 가능한 nadree_w02_test_* MySQL에서 데이터 변환·앱 호출·역변환을 검증한다. callable 인증·App Check·일반관리자 전송 거절·세션 회수·알림 중복·종료 경합을 확인한다. 실제 PayPal 확인은 Sandbox 테스트 계정만 사용한다.
4. 함수별 변경, 데이터 변환, 앱 배포, 서비스 작업과 실패 시 중단 기준을 구체화한 뒤 명시적 승인을 받는다.
5. 승인된 작업창에서 앱 전환과 쓰기·알림 주체를 통제하면서 반영한다. 기존 경로와 새 경로에서 독립적으로 메시지가 생성되는 상태를 방지한다.
6. 승인된 테스트 계정으로 인수 검증을 완료한 뒤 단계적으로 적용 범위를 확대한다. 실제 고객 결제·환불·푸시를 인수 테스트에 사용하지 않는다.

복구는 이전 함수만 배포하는 것으로 끝나지 않는다. 새 구조에 기록된 메시지·읽음·예약 종료를 별도 보존하고 검증된 역변환/매핑으로 이전 구조와 맞춘다. 사전 백업을 무조건 덮어써 전환 후 메시지를 유실하거나 종료 방을 재개하지 않는다. 역변환 미검증이면 쓰기를 차단한 상태로 복구한다.

실패 시 승인된 절차로 callable·Rules·세션 접근과 동기화·푸시·스케줄을 함께 통제한다. 환경변수 false만으로 기존 Firebase 접근이 폐기되지 않는다. 이전 Rules를 복원할 때도 확인된 보안 문제를 재도입하지 않아야 한다. 안전한 이전 구현으로 돌아갈 수 없으면 접근 차단을 유지하고 수정본을 준비한다. 두 알림 발송기를 동시에 켜거나 SQL 컬럼/테이블 삭제로 되돌리지 않는다.

| 방향 승인·코드 보완·운영 전환 | 미실행. 이 검토안의 작성은 실행 승인이 아님 |

이 문서의 권고를 채택할지는 앱·데이터 현황 확인 후 결정한다. 필요한 전환 구현과 검증이 남아 있으므로 전체 출시 완료로 판정하지 않는다.
