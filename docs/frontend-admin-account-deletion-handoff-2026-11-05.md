# 프론트 전달 — 관리자 본인 탈퇴·하위 지점 삭제 API

작성일: 2026-11-05. 대상: 관리자 앱·관리자 웹의 계정 설정/회원탈퇴 담당자.

**서버 반영 완료.** 2026-11-05 11:16 UTC(한국 20:16)에 커밋 `f8b73b1`을 반영하고 API를 재시작했습니다. 실제 공개 OpenAPI에 신규 DELETE 경로와 성공·오류 예시가 제공됩니다. 서버 적용 기록과 격리 테스트를 확인했으며, 실제 관리자·지점 삭제 및 앱 화면 연동은 별도 공동 시험 대상입니다.

## 1. 연결할 API

| 항목 | 내용 |
| --- | --- |
| API 주소 | `https://na-dree.com` |
| 메서드 | **DELETE** |
| 경로 | **`/nadreego/admin/account`** |
| 인증 | `Authorization: Bearer <관리자 accessToken>` |
| 요청 본문 | 없음 |
| 대상 ID/범위 입력 | 없음. adminId·spotMasterId·scope를 보내지 않습니다. |
| 명세 | [Swagger](https://na-dree.com/docs) · [OpenAPI](https://na-dree.com/openapi.json) |

```http
DELETE /nadreego/admin/account HTTP/1.1
Host: na-dree.com
Authorization: Bearer <관리자 accessToken>
```

기존 유효 관리자 세션·활성 지점·계약·직접 manage 권한을 검사합니다. 서버는 **현재 DB 역할**을 기준으로 삭제 범위를 결정하므로 대표권한 양도/승격 후에는 현재 계정 상태를 다시 확인해 안내합니다.

## 2. 권한별 삭제 범위

| 요청자 | 관리자 계정 처리 | 지점 처리 |
| --- | --- | --- |
| 일반관리자 | **요청한 본인만 렌탈 관리자 탈퇴** | 지점 유지 |
| 대표관리자 | **대표 본인 + 본인 지점 + 모든 하위 지점의 렌탈 관리자 전원 탈퇴** | **본인 지점과 모든 하위 지점 삭제** |

대표 요청에는 하위 지점 대표관리자와 일반관리자도 모두 포함됩니다. 모든 깊이의 하위 계층이 대상이며, 상위 지점·형제 지점·다른 회사/계약 지점은 유지됩니다.

**삭제 기준은 로그인한 관리자의 직접 소속 지점입니다.** 화면에서 열어둔 하위 지점에 따라 기준이 바뀌지 않습니다. 화면에서 고른 지점 ID를 넘겨 삭제 범위를 좁히는 기능은 없습니다. 계정 설정의 본인 탈퇴 기능에서 연결해 주세요.

지점은 이력을 보존하는 **논리 삭제**이며, 삭제 후 신규 가입·신규 예약·활성 지점 업무 접근이 차단됩니다. 대상 관리자의 렌탈 역할·본 서비스 로그인 세션·채팅 접근·서버 FCM 연결을 회수합니다. 공유 관리자 식별 정보·다른 서비스 권한·기존 예약/계약/차량/QR/결제 이력은 보존합니다. 진행 중 예약 취소·환불·차량 반납은 자동 실행하지 않습니다.

## 3. 앱·웹 화면에서 처리할 내용

1. 현재 관리자 역할과 직접 소속 지점을 확인해 탈퇴 확인 화면을 표시합니다.
2. 일반관리자에게는 본인 탈퇴, 대표관리자에게는 **본인과 하위 지점 관리자 전원 및 해당 지점 전체 삭제**를 명시합니다. 사용자 확인 버튼에서만 요청하고 중복 클릭을 막습니다.
3. 기존 관리자 accessToken으로 DELETE를 한 번 요청합니다. 대표 탈퇴에는 사전 대표권한 양도가 필요하지 않습니다.
4. HTTP 200과 `status=success`, `deleted=true`를 확인하면 저장한 access/refresh token을 폐기합니다. Firebase 채팅 로그아웃·채팅 구독 해제, 관리자/지점 캐시와 메모리 상태를 정리하고 로그인 화면으로 이동합니다.
5. 뒤로가기로 이전 관리자 화면에 복귀하지 않도록 인증이 필요한 화면의 내비게이션 기록도 정리합니다. 함께 탈퇴된 다른 관리자들은 후속 인증 실패 시 기존 세션 만료 흐름으로 로그아웃합니다.

확인 문구 예시:

- 일반관리자: “회원탈퇴 시 현재 계정의 렌탈 관리자 권한이 해제됩니다. 계속하시겠습니까?”
- 대표관리자: “대표관리자 본인과 현재 소속 지점 및 모든 하위 지점의 관리자 계정이 탈퇴 처리되고, 해당 지점들도 삭제됩니다. 계속하시겠습니까?”

## 4. 성공 응답

일반관리자 — HTTP 200:

```json
{
  "status": "success",
  "deleted": true,
  "scope": "SELF",
  "spotMasterId": "<본인-지점-ID>",
  "deletedAdminCount": 1,
  "deletedSpotCount": 0
}
```

대표관리자 — HTTP 200 예시:

```json
{
  "status": "success",
  "deleted": true,
  "scope": "SUBTREE",
  "spotMasterId": "<본인-지점-ID>",
  "deletedAdminCount": 4,
  "deletedSpotCount": 2
}
```

| 필드 | 의미 |
| --- | --- |
| status / deleted | `success` / `true`이면 처리 완료 |
| scope | `SELF`: 본인만, `SUBTREE`: 본인 지점과 모든 하위 지점 |
| spotMasterId | 삭제 기준이 된 요청자의 직접 소속 지점 ID |
| deletedAdminCount | 렌탈 탈퇴 대상 관리자 수. 대표 요청에는 대표 본인도 포함 |
| deletedSpotCount | 논리 삭제 대상 지점 수. 일반관리자는 0 |

건수는 성공 시 서버가 반환한 값을 사용합니다. 위 4명/2개는 응답 형식 예시이며 실제 삭제가 수행된 테스트 결과가 아닙니다. 이미 비활성인 하위 지점이나 만료된 렌탈 역할도 정리 대상에 포함될 수 있습니다.

## 5. 실패·응답 유실 처리

오류는 기존 `status=fail`, `errorCode` 형태입니다.

```json
{
  "status": "fail",
  "errorCode": "CHAT_SYNC_FAILED"
}
```

| 상황 | 프론트 처리 |
| --- | --- |
| 401 AUTH_REQUIRED | 기존 세션 만료/회수 처리로 로그인 안내. 탈퇴 성공 화면으로 확정하지 않음 |
| 403 RENTAL_ROLE_REQUIRED | 현재 계정의 렌탈 역할 확인. 다른 API로 자동 우회하지 않음 |
| 403 SPOT_ACCESS_DENIED / SPOT_REQUIRED | 직접 소속·manage 권한 확인 안내 |
| 403 SPOT_UNAVAILABLE / SPOT_CONTRACT_INACTIVE | 지점/계약 상태 확인 안내. 이 API도 기존 활성 상태 검사를 적용함 |
| 409 DATA_CONFLICT | 성공으로 표시하지 않고 최신 상태와 처리 결과 확인 안내 |
| 503 CHAT_SYNC_FAILED | 채팅 권한 회수 실패 안내. 관리자·지점 DB 변경은 롤백되며 일부 채팅 세션은 이미 회수됐을 수 있어 기존 채팅 재인증 흐름이 필요할 수 있음 |
| 503 DATABASE_UNAVAILABLE / 기타 서버 오류 | 성공으로 표시하지 않고 처리 결과 확인 안내 |
| 타임아웃·연결 끊김·응답 유실 | 처리 결과 미확인으로 표시하고 자동 재요청 중단. 필요 시 운영 확인 |

**성공 후에는 요청자 본인의 토큰도 폐기되므로 동일 토큰 재호출은 401입니다.** 응답 유실 뒤 받은 401만으로 삭제 성공을 확정할 수 없습니다. 타임아웃/오류에 대한 HTTP 클라이언트의 자동 DELETE 재시도는 비활성화하고, 성공 토큰으로 refresh/재로그인을 반복하지 않습니다. 별도 탈퇴 결과 조회 API는 없습니다.

## 6. 기존 API와 연결 구분

| 목적 | API |

- 건너뜀: 전용 MySQL 환경 검사 11개와 Firestore 에뮬레이터 검사 4개.

공동 시험은 **폐기 가능한 별도 테스트 계층과 계정**을 사용합니다. QR·예약 시험에 공용으로 쓰는 대표/지점은 유지하고, 삭제 시험 전용 계층을 준비합니다. 실제 서비스 배포 점검에서는 관리자나 지점에 DELETE를 호출하지 않았습니다.

1. 일반관리자 요청: 본인만 탈퇴되고 같은 지점의 대표·동료·지점은 유지되는지 확인합니다.
2. 대표 요청: 본인·하위 대표·일반관리자가 모두 탈퇴되고 본인 지점부터 마지막 하위 지점까지 삭제되는지 확인합니다. 상위·형제·다른 회사 지점은 유지되어야 합니다.
3. 요청 후 본인과 대상 관리자들의 토큰/refresh/채팅 접근 차단, 삭제 지점 신규 가입·예약 차단을 확인합니다.
4. 200 수신 후 토큰 정리·로그인 화면·뒤로가기 차단, 401/403/503/응답 유실 시 성공 오표시·자동 재요청이 없는지 확인합니다.
5. 기존 예약·차량·결제 이력 보존과 기존 직원 한 명 지정 삭제 기능을 확인합니다.

API 추가를 위한 별도 프론트 환경변수나 Firebase 프로젝트 설정은 필요하지 않습니다. 현재 관리자 인증과 API 주소를 사용합니다.
