## W00. 공통 기반

현재: **기반 코드·로컬 자동 테스트·이번 범위의 마이그레이션 준비 완료**. 실제 MySQL·Redis·SMTP 연동과 DB 적용/재적용 검증이 남아 그룹 전체는 **부분 완료**다. 준비한 마이그레이션은 관리자 FCM·phone VARCHAR(200)·MSP_SPOT_RENT 8컬럼·MSP_RENTAL_ADMIN_REQUEST·렌탈 역할 행이며, 전체 렌탈 확장 마이그레이션 완료를 뜻하지 않는다.

- 독립 실행 환경, 비밀값 없는 설정 예시, DB 연결·트랜잭션, 기존 인증/role 호환성, 지점 권한 의존성, 로그 마스킹, 오류 응답 기반, 테스트 DB를 준비한다.
- 이미 승인된 렌탈 테이블·관리자 FCM 변경의 마이그레이션을 관리하되 기존 DB와 적용 주체·순서를 조율한다. ERD SQL 실행이나 서비스 시작 시 스키마 자동 생성은 하지 않는다.
- 발리 Asia/Makassar 영업 날짜 처리를 공통화한다. 공유 DB를 쓰는 모든 프로세스에 유효한 잠금·트랜잭션 규칙을 정하고 기존 서버의 동시 쓰기도 확인한다.
- 완료 기준: 테스트 환경 부팅·DB 연결·마이그레이션 적용/재적용·권한 거절·날짜 경계 테스트 통과. 이 단계만으로 업무 API 완료로 표시하지 않는다.

## W01. 인증·계정

현재: **01·02·03·04·05·06·07 구현 완료**. 05의 전화번호는 기존 20자 원문을 암호화해 승인된 VARCHAR(200)에 저장한다. 기본 로그인 기준이며 DB 적용·호환 암호화 키·MFA 흐름과 실제 서비스 연동은 미완료다.

[01 로그인](../../rental-project-master.md#api-01), [02 리프래쉬 토큰](../../rental-project-master.md#api-02), [03 로그아웃](../../rental-project-master.md#api-03), [04 지점체크](../../rental-project-master.md#api-04), [05 관리자업데이트](../../rental-project-master.md#api-05), [06 FCM 토큰 업데이트](../../rental-project-master.md#api-06), [07 비밀번호찾기](../../rental-project-master.md#api-07)

- 로그인/갱신/로그아웃, 본인 정보, 지점 확인, 비밀번호 찾기, 최신 FCM 토큰 갱신을 구현한다. 새 서버가 기존 서버의 세션이나 role 판별을 자동 공유한다고 가정하지 않는다.
- 완료 기준: 정상·만료·잘못된 토큰, 타인 정보 변경 차단, 토큰 교체 후 이전 기기 로그아웃이 최신 토큰을 삭제하지 않는지 검증한다. FCM 발송·재시도 자체는 W09 담당이다.
- 남은 결정: 여러 기기 동시 푸시 수신 여부. 현재 한 관리자 최신 토큰 1개 구조를 승인 없이 확장하지 않는다.

## W02. 지점·관리자 권한

현재: **17·23·28·29·30·31·32·33 구현 완료**. 23의 소개·연락 이메일은 지점 신규 컬럼과, 신청 조회·승인·거절은 신청 테이블과 연결했다. 실제 DB 적용·최초 신청 접수·계정 생성 경로 연결과 MySQL 동시성·실연동 검증은 별도 대기다.

[17 대표관리자 변경](../../rental-project-master.md#api-17), [23 샵 정보 수정](../../rental-project-master.md#api-23), [28 하위조직관리](../../rental-project-master.md#api-28), [29 하위조직 추가](../../rental-project-master.md#api-29), [30 관리자 관리](../../rental-project-master.md#api-30), [31 관리자 삭제](../../rental-project-master.md#api-31), [32 관리자 신청관리](../../rental-project-master.md#api-32), [33 관리자 요청 응답](../../rental-project-master.md#api-33)

- 기존 role 테이블을 사용해 대표/일반관리자를 구분하고, 대표 전용 하위지점 생성·가입 요청 처리·대표 변경·관리자 삭제를 적용한다. 다른 묶음도 이 공통 권한 검사를 사용한다.
- 기존 하위조직 API는 스키마/업무 계약 참조다. 새 서버 자체 구현 또는 기존 서버 호출 중 재사용 방법은 별도 결정하고 기존 웹 권한을 넓히지 않는다.
- 완료 기준: 내 지점/허용 하위 범위, 다른 지점 차단, 일반관리자 제한, 가입 승인 후 일반 role, 대표 교체 동시성·대표 한 명 유지 검증.
- 구현 역할 코드는 rental_primary_admin/rental_manager, 대표 범위는 주 소속 지점으로 제한한다. 가입 신청 저장은 MSP_RENTAL_ADMIN_REQUEST로 확정했다. 기타 지점 설정 권한·다중 지점 운영·최초 대표 지정·가입 접수 서버 연결은 추가 확인이 필요하다.

## 나드리 고객 API

현재: **고객 API 1~11과 FCM 토큰 저장 구현 완료**. UID 로그인·프로필·refresh·로그아웃·가용성/가격·예약 요청·PayPal 주문/캡처·진행/완료 목록·결제 전 취소를 `/api/v1/nadri` 네임스페이스로 제공한다. 고객 access token은 1시간 유효하며 고객 refresh token은 UID당 활성 1개만 `MSP_RENTAL_USER_REFRESH_TOKEN`에 저장한다. 기존 나드리고 관리자 API 38개와 `MSP_DRIVER`·RiderLog 영역은 변경하지 않는다. PayPal Sandbox/Live 자격증명 등록, 새 Firebase 프로젝트 연결 및 운영 DB 마이그레이션 적용은 별도 대기다.

상세 계약은 [나드리 고객 사용자 API 설계](nadri-user-api-design.md), 환불 컬럼은 `migrations/004_payment_refund.sql`을 참조한다. 알림 큐 테이블·워커는 현재 사용하지 않는다.

## W04. 가격·티어

[15 차량 가격 변경](../../rental-project-master.md#api-15), [24 티어 추가 및 수정](../../rental-project-master.md#api-24), [25 티어 목록 조회](../../rental-project-master.md#api-25), [26 티어 삭제](../../rental-project-master.md#api-26)

- 차량 BASIC은 지점 BASIC 세부 구간 우선·공통 BASE 대체, PREMIUM은 차량 지정 요금을 적용한다. BASE 고정 구간과 BASIC 정확 min/max 일치 삭제를 구현한다.
- 완료 기준: cc 경계·중첩 오류·개별 요금 0/NULL 구분·권한별 신규 생성·삭제 후 BASE 대체 검증. 가격 변경으로 확정 예약/결제 금액을 소급 수정하지 않는다.
- 남은 결정: BASE 가격 편집과 BASIC 기존 가격 수정/삭제 권한. 신규 추가의 대표 제한만으로 나머지 권한을 추정하지 않는다.

## W06. 예약·렌트 상태 처리

[16 차량 반납](../../rental-project-master.md#api-16), [18 예약 요청 응답](../../rental-project-master.md#api-18), [19 렌트 승인](../../rental-project-master.md#api-19)

- 핵심 상태 변경 묶음이다. 가용성 계산·가배정/재배정·지점/모델 단위 동시성·예약/계약/차량 상태 전이·이력 저장을 함께 구현한다.
- 승인 예약 > 당일 렌트 > 승인 전 요청을 적용한다. 실제 출고 계약·정비·고정 배정은 움직이지 않는다. 재배정은 같은 모델뿐 아니라 가격 조건도 충족해야 한다.
- 완료 기준: 예약 승인과 현장 출고 경합, 대체 차량 있음/없음, BO 연결·RT 직접 생성, 조기/정상 반납, 반복 반납·롤백 시 부분 상태 저장 방지 테스트.
- 같은 고객·요청 차량·기간의 60초 중복 방지는 `/api/v1/nadri/rental/request`에 적용했다. 고객 API는 관리자 38개와 별도 네임스페이스로 운영한다.
- 남은 결정: 반납 지연 재요청 위험, 프리미엄 포함 예약 견적/요금 보존과 결제·출고 연계. MVP 예약 요청은 관리자 승인 대기시간 없이 유지한다.

- 메인 집계, 차량별 달력, 예약·렌트 통합 이용내역을 구현한다. 요청한 필터를 서버에서 적용하고 그 이후 페이지/totalCount를 계산한다. 기본 상태 필터 없음은 종료·취소·거절·만료 건도 포함한다.
- 목록/상세 공통 items와 latestHistory를 유지한다. 연결 BO는 한 건으로 표시하고 별도 전체 변경 히스토리 조회 API는 만들지 않는다.
- 완료 기준: 진행/종료 혼합 조회·중복 없는 집계·월 경계·정비 만료·REQUESTED 비점유·여러 페이지 검색·조회 전후 상태 변경 검증. 가용성 로직을 조회용으로 따로 재구현하지 않고 W06의 공통 규칙을 사용한다.
- 총수익 등 금액 조회는 기존 명세 필드를 먼저 확인한다. 추가 집계가 필요하면 금액·환불·통화·기간 기준과 API 계약을 승인받고 반영한다. 임의의 매출 API는 추가하지 않는다.

## W08. 결제 결과 연동

[37 PayPal 웹훅 수신](../../rental-project-master.md#api-37)

- 사용자가 밝힌 방향은 실제 결제 이용/연동은 고객 앱 나드리, 관리자 앱 나드리고는 금액 정보 조회 중심이다. 이번 변경으로 결제 전 고객 취소, 승인 후 관리자 취소, PayPal 환불 호출과 환불 웹훅 상태 반영을 추가했다.
- 관리자 38개 명세의 PayPal 웹훅과 별도로 나드리 고객 결제 주문·캡처 API를 추가했다. 결제/이벤트 저장과 고객 payment 응답을 연결하며, PayPal 실자격증명·웹훅 등록은 운영 전 확인이 필요하다.
- 완료 기준: Sandbox 서명 검증, 이벤트 중복·순서 역전·금액/통화/계정 불일치·환불·재처리 테스트. 결제 성공만으로 예약 승인/출고를 자동 실행하지 않는다. 결제 완료 후 관리자 취소는 PayPal 캡처 환불을 요청하고, 최종 완료는 웹훅으로 확정한다.
- 나드리 결제 서버의 주문/캡처 식별자·내부 계약 연결·결제 확인 후 출고 조건은 양쪽 서버 간 계약을 확정해야 한다. 이 확인 전에는 실제 출고 연동 완료로 표시하지 않는다.

## W10. 통합 검증·배포

- 묶음별 테스트는 해당 작업 중 수행하며 마지막 단계까지 미루지 않는다. W10에서는 앱 흐름과 공유 DB를 사용하는 기존 서버까지 연결해 회귀·동시성·부하를 확인한다.
- 전체 흐름: 로그인 → 지점/차량/요금/배송 설정 → 예약 또는 현장 렌트 → 조회 → 반납 → 종료 내역 → 결제 결과 반영. 알림은 새 Firebase 연결 이후 추가한다.
- 필수 검증: 기존 웹/API 영향, 마이그레이션 적용 주체, 권한 우회, 발리 자정, 동시 예약/렌트·재배정, 오래된 QR/토큰/반납 요청, 부분 실패와 재처리.
- 같은 모델 25대·1주 요청 등 대표 부하를 측정한다. 문서상의 예상 속도를 성능 보장으로 사용하지 않는다.
- 배포 전 확인: 비밀값 분리·로그 마스킹·운영 설정·작업 중복 제어·배포/복구 절차·실제 앱 연동. 운영 DB 적용은 별도 승인한다.

## 권장 순서와 병렬 작업

1. W00 기반, 이어서 W01 인증과 W02 공통 지점/역할 검증을 먼저 구축한다.
2. W03 차량·QR을 준비하고, W04 가격과 W05 배송은 데이터/권한 계약이 정해지면 나눠 작업한다.
3. W06 공통 상태·가용성 처리와 W07 조회를 맞춘다. 조회 뼈대는 테스트 데이터로 먼저 만들 수 있지만 완료 검증은 실제 상태 전이와 연결한다.
4. W08 결제 결과 연동은 DB와 식별자 계약이 준비되면 병렬 진행한다. 실제 출고를 릴리스하기 전 결제·출고 연결 조건을 검증한다.
5. W09 내부 작업을 각 묶음과 함께 구현하고 W10 앱·기존 서버 통합 검증을 마친다.

병렬 작업은 파일만 분리하는 것으로 충분하지 않다. 공통 모델·인증·상태 전이·잠금 순서와 마이그레이션 적용 책임을 먼저 맞추고, 같은 DB 테이블 변경은 한 곳에서 조율한다.

## 완료 표시 기준

개별 구현 상태는 `미착수`, `부분 완료`, `완료`, `보류`로 표시한다. **완료**는 명시한 기본 기능의 코드·로컬 테스트 완료이며, 실연동과 배포는 별도 상태로 확인한다. 일부 API만 끝났거나 필수 연동 검증이 남았다면 묶음 전체를 완료로 바꾸지 않는다.

W00~W02 전체는 실연동이 남아 **부분 완료**다. W01·W02 개별 API는 기본 기능 구현 완료 15개·부분 완료 0개·보류 0개다. 실제 DB 적용·호환 암호화 키·MFA·최초 가입 신청 접수 연결·의존 서비스 연동은 미완료다. 32·33은 저장된 신청의 조회·처리 완료 기준이다. 완료된 범위와 남은 조건은 [구현 기록](w00-w02-implementation.md)에 함께 표시한다. W03 이후는 미착수다.
