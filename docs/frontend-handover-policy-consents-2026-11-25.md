# 프론트 전달 — 인계별 개인정보처리방침·이용약관 동의

> **사용자 최종 정정으로 이 문서의 인계용 저장 API는 폐기 대상이다.** 새 방식은 회원가입/로그인과 프로필 저장·조회이며, 인계의 두 컬럼도 이관 후 삭제한다. [최신 전달·이관 문서](member-policy-consents-2026-11-25.md)를 사용한다. 최종 정정은 아직 서버 미적용이며, 아래 내용은 `2ccd9c0` 인계 단위 배포 당시 기록으로 보존한다.

**2026-11-25 서버 적용 완료. 고객 앱의 동의 저장과 관리자 앱의 조회 연동을 진행할 수 있다.** 서비스는 기존 공개 API `https://na-dree.com`을 사용하며 [Swagger](https://na-dree.com/docs)에 반영됐다.

이 문서는 [서버 적용 결과](handover-policy-consents-server-verification-2026-11-25.md)를 기준으로 작성했다. 배포 코드는 `2ccd9c0`, 결과 문서는 `7bb7503`이며 최종 서버 확인은 **2026-11-25 06:30:15 UTC / 발리 14:30:15**다. 이 문서 작성 과정에서 서버에 새 업무 요청을 실행하지 않았다.

## 바뀐 내용

- 인계마다 **개인정보처리방침 동의 시각**과 **이용약관 동의 시각**을 따로 저장한다.
- 고객 프로필에 저장하지 않는다. 동의한 고객과 대상은 기존 인계의 고객 ID·인계 ID로 식별한다.
- 서버가 최초 동의 시각을 UTC 초 단위로 기록하며, 재요청해도 해당 시각을 유지한다.
- 기존 인계 7건은 두 시각을 NULL로 보존했다. 기존 서명 시각으로 대신 채우지 않았다.
- 기존 폼·영상·서명 완료 API와 렌트 시작 조건은 유지한다. **새 동의 API 호출만으로 서명 완료나 렌트 시작 가능 상태가 되지 않는다.**

## 고객 앱 저장 요청

**POST `/api/v1/nadree/rental/handovers/{handover_id}/consents`**

```http
Authorization: Bearer <Nadree customer access token>
Content-Type: application/json
```

Nadree 고객 로그인으로 발급받은 access token을 사용한다. 관리자 토큰으로 대신 저장할 수 없다. 고객 본인의 인계를 **실제로 시작한 후**, 렌트 시작 또는 인계 취소 전에 호출한다. 관리자 승인으로 인계 ID만 준비된 `NOT_STARTED` 단계에서는 409다. 폼·영상 완료 전에도 기록할 수 있다.

두 항목을 함께 동의한 경우:

```json
{
  "privacyPolicyAgreed": true,
  "termsAgreed": true
}
```

하나씩 동의한다면 다음처럼 따로 호출한다.

```json
{"privacyPolicyAgreed": true}
```

```json
{"termsAgreed": true}
```

고객이 실제로 체크한 항목만 JSON `true`로 보낸다. 하나 이상의 항목이 필요하다. 생략한 항목은 변경하지 않으며 `false`로 철회하는 기능은 없다. 빈 본문, `false`, `null`, `"true"`, `1`, 고객이 지정한 시각·UID 등은 422다. 별도 요청 ID나 동의 시각을 만들 필요가 없다.

## 응답과 화면 표시

성공은 HTTP 200, 기존 `HandoverResult` 전체 형식인 `status:"success"`와 `item`이다. 다음은 `item`에서 추가 필드만 발췌한 예시다.

```json
{
  "privacyPolicyAgreedAt": "2026-11-25T06:28:20Z",
  "termsAgreedAt": "2026-11-25T06:28:23Z"
}
```

| 필드 | 화면 의미 |
| --- | --- |
| `privacyPolicyAgreedAt` | 해당 인계의 개인정보처리방침 최초 동의 시각 |
| `termsAgreedAt` | 해당 인계의 이용약관 최초 동의 시각 |
| `null` | 해당 항목의 시각 미기록. 과거 고객이 거부했다는 이력으로 단정하지 않음 |

두 항목을 함께 처음 저장하면 같은 시각을 기록한다. 따로 저장하면 각각 최초 시각을 보관한다. 이미 저장된 항목과 새 항목을 함께 보내도 기존 시각은 유지한다. 문자열은 UTC로 해석해 앱 표시 시간대로 변환한다. 위 시각은 형식 설명용 가상 예시다.

실제 서버에서 조회를 확인한 위치:

- 고객 인계 상세: `GET /api/v1/nadree/rental/handovers/{handover_id}`의 `item`.
- 고객 예약 상세: `GET /api/v1/nadree/rental/reservations/{reservation_id}`의 `item.handover`.
- 대표·일반관리자 인계 상세: `GET /nadreego/handovers/{handover_id}`의 `item`.
- 관리자 인계 목록: `GET /nadreego/handovers`의 각 항목.

관리자 예약 상세·고객 렌트 상세도 기존 handover 진행 정보에 두 필드를 반환하는 계약이지만, 이번 실서버 시험에서는 해당 두 조회를 실행하지 않았다. 고객 프로필 API에는 추가하지 않았다.

새 인계는 NULL부터 시작한다. 수정안 거부 후 새 인계를 시작할 때도 새 `handoverId`의 기록을 사용한다. 다른 인계의 동의 시각이나 `signatureCompletedAt`를 복사해 표시하지 않는다.

## 재시도와 오류 처리

| HTTP / errorCode | 앱 처리 |
| --- | --- |
| 200 | 반환된 두 시각과 현재 인계 진행 상태를 반영 |
| 401 `INVALID_NADRI_USER_TOKEN` | 고객 로그인/토큰 확인. 서버 시험 로그인으로 기존 앱 세션이 회수됐을 수 있어 재로그인 필요 가능 |
| 404 `HANDOVER_REQUIRED` | 미존재·타 고객 인계. 대상 ID/소유 범위 확인 |
| 409 `HANDOVER_CLOSED` | 미시작·취소·렌트 시작 등 현재 쓰기 불가. 최신 인계 상세 조회 |
| 422 `INVALID_INPUT` | 하나 이상의 명시적 true 불리언만 전송 |
| 503 `HANDOVER_SCHEMA_UPDATE_REQUIRED` | 서버 스키마 확인 요청. 이번 적용 시 마이그레이션 잔여 0개 확인 완료 |

응답 유실 시 같은 인계 상세부터 조회한다. 아직 열린 인계라면 같은 true 항목으로 재요청할 수 있고 최초 시각은 바뀌지 않는다. 이미 렌트를 시작했거나 취소한 뒤에는 재요청도 409이므로 상세에 보관된 결과를 사용한다. 실패만으로 새 인계를 만들거나 예약을 자동 취소하지 않는다.

## 서버 검증 결과와 프론트 확인 순서

서버에서 nullable 동의 컬럼 2개를 적용하고 인계 **37컬럼**, 마이그레이션 잔여 **0개**, API 재시작·공개/로컬 health·Swagger 정상, **106경로/112메서드**를 확인했다. env·암호화 키·Firebase·S3·타이머 설정 변경은 없다.

관련 격리 **68건 통과**에는 별도 MySQL DB의 동시 요청·최초 시각 보존이 포함된다. 실제 서버의 **50개 HTTP 검사 기록**도 기대 결과를 충족했다. 분포는 200 33건·409 5건·401 3건·422 8건·404 1건이며, 의도한 오류 응답을 포함한다. 50개 모두 성공 응답이거나 독립 테스트 50개라는 의미는 아니다.

실제 확인한 항목은 개별/동시 최초 저장, 중복 재요청·동시 POST의 시각 불변, 위 상세·목록 조회, 엄격한 true 입력, 관리자·무인증 차단, 미시작·취소·기존 STARTED 인계 차단이다. 타 고객 차단은 승인된 고객이 **타 고객의 기존 닫힌 인계**에 접근해 404와 기존 행 불변을 확인했다. 두 번째 고객으로 로그인해 새 인계에 접근하는 방향은 격리 검증만 통과했다.

프론트에서는 다음을 확인한다.

1. 기존 테스트 고객으로 로그인하고 새 승인 예약의 인계를 시작한다. 승인 직후 ID만 받은 상태와 실제 시작 상태를 구분한다.
2. 한 항목을 체크해 저장한 뒤 나머지 항목을 저장한다. 첫 시각이 유지되는지 확인한다. 별도 새 인계에서는 두 항목을 함께 저장한다.
3. 화면 재진입·앱 재실행·응답 유실 후 상세로 두 시각을 복구한다. 관리자 상세·목록에서도 같은 값을 표시한다.
4. 관리자 토큰·다른 고객으로 저장 시도, 취소/렌트 시작 후 재요청을 확인한다. 기존 시험 로그인 때문에 세션이 끊겼다면 재로그인한다.
5. 동의 기록 후에도 기존 폼→영상→서명·관리자 확인→담당자 렌트 시작 절차를 이어서 전체 흐름을 확인한다.

이번 서버 시험은 새 Walk-in/인계 2건을 만들어 검증 후 정상 취소했고, 시험 미완료 0건·차량 AVAILABLE을 확인했다. 기존 7건과 다른 업무는 보존했다. **새 동의를 포함한 서류·S3·서명·렌트 시작 전체 실연동, 실제 앱 UI·App Check·기기 FCM은 이번에 검증하지 않았다.** 새 동의 함수는 알림을 큐에 넣지 않는 구현이며, 동의 API만의 실제 FCM 전송 수를 계측한 것은 아니다.

새 동의 API를 사용하기 위해 프론트가 별도 env·암호화 키·Firebase 배포를 준비할 필요는 없다. 기존 인증 설정으로 새 API와 필드를 연결하면 된다. 전체 계약·재적용 절차는 [동의 API 문서](handover-policy-consents-2026-11-25.md), 실제 검증의 상세 범위는 [서버 결과](handover-policy-consents-server-verification-2026-11-25.md)를 참고한다.
