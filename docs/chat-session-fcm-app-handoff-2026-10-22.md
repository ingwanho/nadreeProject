# 앱 담당자 전달: 채팅 세션·FCM 토큰 갱신 처리

최종 갱신일: 2026-10-27. 고객 앱과 관리자 앱의 연동·검증 작업만 정리한다. API·Firestore·callable 계약은 [채팅 계약](../chat/chat-contract.md)을 따른다. 앱 소스와 실기기 검증 결과는 제공되지 않아 아래 항목의 앱 구현 완료 여부는 아직 확인하지 않았다.

서버 반영 완료: **동일 FCM 토큰 재등록 시 기존 채팅 세션 유지, 실제 토큰 변경 시 기존 채팅 세션 회수**가 적용됐다. 이미 회수된 세션이 자동으로 복구되지는 않는다. 실제 토큰 변경 후 재연결과 이미 해제된 세션의 복구는 앱에서 아래 순서로 처리한다.

## 1. 앱이 처리할 순서

최초 업무 로그인 또는 채팅 연결이 필요한 경우 다음 순서로 실행한다.

1. 유효한 업무 access/refresh 토큰을 확보한다. 계정을 새로 만들거나 채팅 데이터를 초기화할 필요는 없다.
2. 기기 FCM 토큰을 얻은 경우 업무 API에 저장하고 성공 응답을 기다린다. 앱에 토큰 문자열을 저장하는 것만으로 서버 등록이 끝나지 않는다.
3. 같은 업무 계정의 채팅 세션 API를 호출한다.
4. 응답의 firebaseCustomToken으로 Firebase SDK의 signInWithCustomToken을 수행한다.
5. 인증 성공 후 Firestore 방/메시지/읽음 구독을 연결하고 callable을 사용한다. 연결 중에는 메시지 전송을 기다리게 한다.

Firebase 프로젝트는 bail-472405, Functions 리전은 asia-southeast2, Firestore는 (default)다. 기존 App Check 검증을 유지하고 callable에 유효한 App Check 토큰이 전달되도록 한다.

## 2. FCM 토큰 저장 API

| 앱 | 메서드·경로 | 인증 | 본문 |
| --- | --- | --- | --- |
| 고객 | PATCH `/api/v1/nadree/user/profile` | 고객 업무 access token의 Authorization Bearer | `{"fcmToken":"<현재 기기 FCM 토큰>"}` |
| 관리자 | POST `/nadreego/admin/fcmToken` | 관리자 업무 access token의 Authorization Bearer | `{"fcmToken":"<현재 기기 FCM 토큰>"}` |

관리자의 일반 프로필 수정에 fcmToken을 함께 보내는 기존 경로도 유지하지만, 정기 토큰 등록에는 위 전용 API를 사용한다. 이름 등 일반 프로필을 저장할 때는 변경한 필드만 보내고 fcmToken을 매번 자동 첨부하지 않는다.

FCM SDK의 토큰 갱신 이벤트를 처리한다. 실제 토큰이 변경되면 **서버 저장 성공 → 새 채팅 세션 발급 → Firebase 재로그인 → 구독 재연결**을 순서대로 수행한다. 서버 저장과 세션 발급을 동시에 실행하지 않는다.

같은 계정의 이미 등록된 동일 토큰은 반복 저장할 필요가 없다. 등록 성공 여부는 계정별로 관리하며, 다른 계정 로그인 시 기기 토큰이 같아도 새 계정에 다시 등록한다. 서버 등록에 실패한 값을 등록 완료로 캐시하지 않는다. FCM 토큰을 얻지 못한 상태와 채팅 인증 실패를 구분하고, null/빈 토큰을 임의로 전송하지 않는다.

## 3. 채팅 세션 발급 API

| 앱 | 메서드·경로 | 인증 | 본문 |
| --- | --- | --- | --- |
| 고객 | POST `/api/v1/nadree/user/chat/session` | 고객 Authorization Bearer + **현재 X-Refresh-Token** | 없음 |
| 관리자 | POST `/nadreego/chat/session` | 관리자 Authorization Bearer | 없음 |

여기의 Bearer는 백엔드 업무 access token이다. Firebase ID Token이나 FCM 토큰을 대신 보내지 않는다. access/refresh 갱신 후에는 최신 토큰 쌍을 사용한다.

응답의 firebaseCustomToken, firebaseUid, managerId, shops, region을 기존 계약대로 사용한다. UID·세션 ID·지점 권한을 앱이 임의 지정하지 않는다. Firebase 로그인에는 응답의 custom token을 사용하고, 이 토큰을 FCM 등록 토큰으로 저장하지 않는다.

업무 로그인 세션이 유효한데 채팅만 해제된 경우, 업무 계정 재가입/강제 로그아웃 없이 위 채팅 세션 API로 재연결한다. **이미 비활성화된 세션은 동일 FCM 토큰을 다시 저장하는 것만으로 복구되지 않는다.** 채팅 세션 API를 한 번 발급받아 Firebase에 다시 로그인해야 한다. 기존 Firebase ID Token만 새로 고치는 것으로 서버의 채팅 세션 회수가 해제되지는 않는다.

## 4. 중복 연결과 앱 복귀 처리

- 로그인·토큰 갱신·채팅 복구를 담당하는 곳을 하나로 둔다. 화면마다 세션을 발급하면 새 발급이 앞선 세션을 무효화한다.
- 동시에 발생한 동일 연결 요청을 하나로 합친다. 처리 중 토큰이 새로 바뀌면 현재 작업 이후 최신 값으로 처리하고, 늦게 도착한 이전 응답이 최신 연결을 덮어쓰지 않게 한다.
- 세션 교체 시 기존 Firestore 리스너를 정리하고 새 Firebase 인증 후 재구독한다. 메시지와 읽음 요약을 다시 조회한다.
- 앱 복귀 시 연결 상태를 확인하고, 정상 연결이면 매번 세션을 새로 발급하지 않는다. 회수/만료 오류가 있으면 복구한다.
- 명시적인 로그아웃·계정 전환에서는 리스너와 해당 계정의 로컬 채팅 캐시를 정리한다. 로그아웃된 계정의 세션을 자동 재발급하지 않는다.
- 앱 백그라운드 전환/종료 테스트와 명시적인 업무 로그아웃을 구분한다. 로그아웃으로 세션을 회수한 뒤에는 해당 세션의 푸시를 기대하지 않는다.

## 5. 오류별 처리

| 상황 | 앱 처리 |
| --- | --- |
| callable의 unauthenticated / CHAT_SESSION_REQUIRED | 업무 세션이 유효하면 채팅 세션을 한 번 재발급하고 Firebase 재로그인 후 다시 연결한다. |
| Firestore permission-denied | 세션 회수인지 실제 방/지점 권한 거절인지 구분한다. 유효한 업무 세션에서 한 번 복구한 뒤에도 거절되면 권한 오류로 표시한다. |
| 세션 API 401 | 업무 access 만료는 기존 refresh 절차로 갱신한다. refresh 폐기/만료·토큰 쌍 불일치는 기존 로그인 절차로 처리한다. 채팅 세션 요청을 무한 반복하지 않는다. |
| 세션 API 403·CHAT_ACCESS_DENIED | 역할·소속·방 접근 권한 오류로 처리한다. 재발급으로 우회하지 않는다. |
| CHAT_READ_ONLY | 종료 상태를 표시하고 전송 UI를 비활성화한다. 같은 방을 재개하거나 계속 전송하지 않는다. |
| 429·503·통신 오류 | 간격을 둔 제한 재시도를 제공한다. 연결 성공으로 표시하거나 동시 재발급하지 않는다. |
| App Check 검증 실패 | App Check 등록·토큰 전달 문제로 처리한다. 세션 재발급을 반복하거나 검증을 해제하지 않는다. |

메시지를 재시도할 때는 최초에 생성한 동일 messageId·본문을 유지한다. 인증 복구 후 같은 메시지를 재시도하면서 ID를 새로 만들면 중복 메시지가 생길 수 있다.

## 6. 푸시 표시와 건수 해석

2026-10-27 반영: 모든 새 메시지의 이벤트가 생성되면 서버가 푸시 발송을 시도한다. 채팅방의 첫 메시지에만 적용되는 기능이 아니다. 실패·미처리 건은 기존 30초 작업으로 복구한다. 일시 실패는 같은 수신 계정·업무 세션·채팅 세션·FCM 토큰에 한해 최초 발송 포함 최대 5회, 메시지 생성 후 1시간 이내 재시도한다. 함수 기동·네트워크·기기 상태에 따라 표시 시각은 늦어질 수 있다. 앱 요청·응답 필드 변경은 없으며 앱에서 서버 내부 콜백 API를 호출하지 않는다.

FCM이 접수한 직후 서버의 결과 저장이 실패하면 같은 eventId가 다시 올 수 있다. 앱은 **동일 eventId를 한 번만 표시**하고 전경·백그라운드 표시 경로 모두에 같은 중복 방지를 적용한다. 서버가 재시도하더라도 이미 표시한 이벤트를 다시 표시하지 않는다.

푸시 수신 순서를 메시지 순서로 사용하지 않는다. 방 내용은 기존 Firestore `sequence` 기준으로 정렬하고, 앱 복귀 시 실제 메시지·읽음 위치를 다시 조회한다. [Firestore 트리거의 중복·순서 특성](https://firebase.google.com/docs/functions/firestore-events)

로그아웃·세션 만료·토큰 변경·권한 변경으로 수신 자격이 사라지면 재시도는 중단된다. 로그인 복구 시 과거 푸시가 모두 재발송된다고 가정하지 말고, 권한이 허용된 최신 메시지·읽음 요약·알림함을 다시 조회한다. FCM 접수 기록은 실기기 수신이나 알림 화면 표시 성공을 뜻하지 않는다.

현재 채팅 푸시 data는 eventId, shopId, roomId다. 채팅 분기에 `data.type`이나 메시지 본문이 반드시 있다고 가정하지 않는다. eventId의 `chat:` 구분과 기존 업무 알림 분기를 함께 처리한다. 알림을 누르면 roomId로 권한이 허용된 방의 내용을 조회한다.

- 같은 eventId는 한 번만 표시한다. 전경/백그라운드에서 플랫폼의 알림 표시와 앱의 직접 표시가 겹치지 않도록 한다.
- 고객이 보낸 메시지의 알림 대상은 관리자이며, 관리자 메시지는 해당 고객이 대상이다. 자기 발신 메시지까지 고객 푸시 수신 건수에 합산하지 않는다.
- 메시지·알림함 저장과 FCM 실제 수신을 구분한다. 서버의 알림함 처리 완료가 기기 수신 성공을 보장하지 않는다.
- 누락된 이전 푸시가 채팅 세션 복구 후 자동 재전송된다고 가정하지 않는다. 앱 복귀 시 Firestore 메시지·읽음 요약을 다시 조회한다. 관리자 공통 알림함은 기존 관리자 API로 별도 조회한다.
- 메시지 수·사용자별 푸시 수·프로젝트 전체 FCM 집계를 구분한다. 콘솔 집계에는 다른 업무 알림과 집계 지연도 영향을 줄 수 있다. [Firebase 집계 안내](https://firebase.google.com/docs/cloud-messaging/understand-delivery).

FCM/custom/ID/access/refresh/App Check 토큰·고객 UID·메시지 본문을 로그나 분석 이벤트에 남기지 않는다. 문제 재현 자료에는 시각·앱 빌드·상태 코드·고정 오류 코드·개인정보 없는 건수만 사용한다.

## 7. 앱 검증 체크리스트

아래는 앱 담당자가 수행할 검사다. 서버 자동 테스트 통과를 앱·실기기 검증 통과로 대체하지 않는다.

| 검사 | 기대 결과 |
| --- | --- |
| 최초 연결 | FCM 저장 성공 후 세션 발급·Firebase 로그인·방 구독·메시지 호출 성공 |
| 동일 FCM 토큰 재등록 반복 | 기존 채팅 연결과 수신이 유지되고 불필요한 세션 재발급/재로그인 없음 |
| 일반 프로필 수정 | 변경 필드만 저장하며 정상 채팅 연결 유지 |
| 실제 FCM 토큰 변경 | 새 토큰 저장 이후 세션 재발급·Firebase 재로그인·재구독 완료 |
| 이미 회수된 세션 복구 | 유효한 업무 세션으로 채팅만 재발급; 신규 가입/채팅 데이터 초기화 없이 복구 |
| 동시에 여러 화면 진입 | 세션 발급과 리스너가 중복되지 않고 연결이 서로 끊기지 않음 |
| 복구 중 새 토큰 도착 | 마지막 토큰과 마지막 세션이 연결에 사용됨 |
| 대표→고객 메시지 | 메시지 1건·수신 고객의 알림 처리, 전경/백그라운드 중복 표시 없음 |
| 고객→관리자 메시지 | 해당 지점의 유효한 관리자 수신, 발신 고객의 자기 알림으로 합산하지 않음 |
| 동일 messageId 재시도 | 메시지 추가 생성이나 중복 알림 표시 없이 기존 결과 사용 |
| 앱 복귀·푸시 누락 | 실제 방 내용/읽음 요약을 다시 불러와 누락 내용 표시 |
| 업무 로그아웃/계정 전환 | 이전 리스너·캐시 정리, 이전 계정으로 자동 재연결/푸시 표시 없음 |
| 일반관리자·다른 지점·종료 방 | 조회/답변/접근 제한이 기존 계약대로 유지됨 |
| 실패 응답 | 401/403/429/503·App Check 실패가 구분되고 무한 재발급 없음 |

승인된 테스트 계정·지점·기기만 사용한다. 앱 빌드/버전, 플랫폼, 실행 시각, 수행 항목별 성공/실패, 고정 오류 코드와 개인정보 없는 건수를 서버 담당자에게 전달한다. 실제 토큰·계정 정보는 전달 문서에 포함하지 않는다.
